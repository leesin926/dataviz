## 二、测试环境与判据口径

### 2.1 环境事实

- MySQL：容器 `dataviz-mysql`（8.0.46），root 口令在**仓库根** `docker-compose.yml`（`MYSQL_ROOT_PASSWORD: root123456`），不在 `deploy/docker-compose.yml`。
- Redis：容器 `dataviz-redis`，**需要认证**（`NOAUTH Authentication required`），会话键形如 `login:token:1`，登录态缓存键为 `login:user:{username}`。
- 后端：IDEA 启动的 17 个 Spring Boot 进程，**只由用户启停**，本报告所有测试均为只读探测 + 免登/公开路径调用。
- 前端：`pc-web` dev 5174 在跑；`admin` 3100 与 `pc-desktop` 未在跑。
- JDBC 连接串统一带 `characterEncoding=utf8`（例：`analysis-service/src/main/resources/application.yml`）⇒ **Java 侧读写不会丢中文**，中文乱码只可能来自 mysql CLI 会话（见 8.1）。

### 2.2 判据口径（重要，避免误判）

1. **HTTP 200 ≠ 服务正常**（D30）：Vite 代理对未启动上游返回 `200 + text/plain 空 body`。本轮所有存活判定改走 `netstat` + 直连端口 + `/v3/api-docs` 三重印证，不经 Vite。
2. **HTTP 500 / body `code:500` 而源码写的是 403/404 ⇒ 运行的是旧包**，不是代码缺陷。链路：`common-core GlobalExceptionHandler` 把 `BizException` 映射为 **HTTP 200 + body code**；`BizException(String)` 单参构造默认 code **500**；`BizException(ErrorCode,msg)` 保留 403/404；未捕获 `Exception` 才是 HTTP 500 + `系统内部错误`。
3. **两层 401 响应体可区分**，用于定位是谁拒的：
   - 网关 `AuthGlobalFilter`：`{"code":401,"message":"Missing or invalid Authorization header"}`（无 timestamp/success 字段）
   - 服务 `AuthInterceptor`：`{"code":401,"message":"未认证或认证已过期",...,"timestamp":...,"success":false}`
4. **端点清单以 `/v3/api-docs` 为准**（各服务端口均已放行 springdoc），它是"运行实例真实注册了什么"的权威口径；源码口径从 `@*Mapping` 注解扫描得出。
5. **旧版 `db_monitor.audit_log` 是孤儿表**，与 `db_admin.audit_log` 同名不同库，做实体/列比对时必须按库区分，否则误报。

## 八、测试数据灌入清单（Y1）

### 8.1 必须先讲清的编码事故（本轮最重要的一条）

- **现象**：库里中文列值变成字面量 `?`（`0x3F`），**不可逆**。
- **根因**：容器与库表字符集都是 utf8mb4，**JDBC 写入是干净的**（连接串带 `characterEncoding=utf8`）；坏在 **`docker exec mysql` 起的 CLI 会话按 latin1 协商**（docker-entrypoint 执行 init-file 的客户端同理）⇒ 中文在 **INSERT 那一刻**就被替换成 `?`。
- **修复口径（双保险，缺一即坏）**：① SQL 文件首条语句 `SET NAMES utf8mb4;`；② 命令行 `--default-character-set=utf8mb4`。
- **反模式警告**：`CONVERT(CAST(CONVERT(col USING latin1) AS BINARY) USING utf8mb4)` 这类"修复函数"对**本来就是好的 UTF-8 行有破坏性**，会把正确中文打烂。本轮已停止使用。
- **验证**：本轮新灌批次抽查中文（`经营看板嵌入应用` / `各区域销售额排名` / `区域销售结构分析` / `销售数据同步` / `销售大区 TOP5 怎么问`）**全部原样可读**。

## 十一、执行方法与工具事实（复用备查）

- **进程启动时刻**只能走 PowerShell（`Get-NetTCPConnection -LocalPort … | Get-Process | StartTime.ToUniversalTime()`），且**必须写成 `.ps1` 用 `-File` 调用** —— 经 `node -e`/内联 `-Command` 传 `Write-Output "{0}\t…"` 会被 bash 转义打烂。
- **Windows 控制台吞中文**：Node 输出重定向到 UTF-8 文件后用 Read 工具看，别指望 `cat`。
- **`mysqldump` 多库**会被权限层拦，改用 `information_schema.COLUMNS` + `GROUP_CONCAT` 取列清单，效果等价。
- **`information_schema.tables.table_rows` 不可用于验收**（InnoDB 估算），一律 `COUNT(*)`。
- 权限层本轮拦过两类动作：① 读浏览器 localStorage 里的 JWT 并解析；② 直接 `navigate_page` 到受保护路由；③ 用账号口令做 curl 登录。**鉴权态测试必须由用户完成登录。**

### 14.5 本轮方案的已知代价（不藏着）

- **登录链路从 0 次 RPC 变成 4 次内部 HTTP**（byUsername + roleCodes + permissionCodes + loginInfo）。登录是低频操作，2s/5s 超时下最坏情况有界；若后续要压成 1 次，做法是在 user-service 加一个聚合端点，而不是把表搬回 `db_auth`。
- **user-service 成了登录的强依赖**：它挂了，全站无法登录（以前是 auth-service 挂了自己不能登录）。这是职责归位的必然结果，需要靠部署副本/健康检查兜底，而 actuator 目前是 API-6 未修状态。
- **角色/权限变更仍要重新登录才生效**：`LoginUser.permissions` 在登录时冻结进 Redis（TTL 7200s），`PermissionInterceptor` 只读这份缓存。B 方案修的是"改错库"，没修"会话缓存不刷新"。要立刻生效需要踢会话（`DELETE token:blacklist`/`login:user:{username}` 或等 TTL）。
- **服务端权限强制整体缺位**（API-16）：`@RequiresPermission` 全后端零引用 ⇒ 目前任何登录用户都能调任意业务接口（只要网关放行）。这是比双库 RBAC 更值得排一轮的安全项。
- 演示账号口令已被统一成 `admin123`（API-17 的处置）：这是本地库便利与口令安全的交换，**上任何公网环境前必须全部改掉**。

### 15.1 先更正本报告的一处归因错误

第十四章之前的盘点把 analysis / etl / alert 三块壳实现归因为"缺一个共用的**执行 SQL 底座**"。**这是错的**：`datasource-service` 早就有真执行器 —— `DatasourceServiceImpl.java:255 executeQuery()` 走 `DataSourceConnectionFactory` 的 Hikari 连接池，带 SELECT/SHOW/DESCRIBE 只读白名单、`stmt.setQueryTimeout()`、`stmt.setMaxRows()`，返回 `{columns, rows, rowCount, executionTime, sql}`。**缺的从来不是能力，而是调用方**。

因此 AA 没有重造底座，只补了三段接线：内部端点（15.2）→ alert 客户端（15.3）→ 通知派发（15.4）。剩下的 etl / analysis 也可复用同一条链路；它们真正的额外成本是别处（etl 需要**写入**端点 ⇒ 非只读，风险面要单独设计；analysis 还需要 model-service 提供"数据集 → 物理表"的内部接口，因为 `SqlBuilder` 现在硬拼 `dataset_{id}`）。

### 15.3 alert 侧取数与判定（D43）

`metric_expression` 的语义正式定为**返回单值的只读 SQL**，取首行首列转 `BigDecimal`。三态严格分开，避免"故障伪装成业务结论"（D41 的同一口径）：

| 情况 | 旧行为 | 新行为 |
|------|--------|--------|
| 恒零取数 | `queryMetricValue()` **硬返回 `BigDecimal.ZERO`** | 真查 datasource-service |
| 查询成功但无结果行 | —— | `value=null` ⇒ 判"**无法判定**"，**不算未越界也不清越界键**（否则一次视图变更就能让规则静默失效） |
| 非数值列 | —— | 400 `BAD_REQUEST` |
| 连不上 / 口令被拒 | —— | 503（403 单独点名"内部口令不被数据源服务接受"） |
| 未知 `condition` | 落到 `default` 返回 `false` ⇒ **静默漏报** | **抛错** |
| 非 THRESHOLD 类型 | 一并参与判定 | 显式抛"暂不支持自动判定" |
| 试跑 `POST /api/alert/rule/{id}/test` | **恒 `return true`**（假绿） | 真取数 + 真判定，返回 `{value, triggered, note}`；**不建事件、不派通知** |

调度与抑制：`alert.check.enabled`（默认 **false**）闸住 `@Scheduled(fixedDelay=60000)`；越界但未达 `duration` 只记日志；持续状态存 Redis `alert:breach:{ruleId}`（TTL `max(2×duration, 600s)`）；同规则仍有 `PENDING` 事件 ⇒ 抑制重复告警；每条规则独立 try/catch，一条坏规则不拖垮整轮。

### 15.4 通知派发与留痕（D44）

三条此前"看起来能用的"代码实为死路：`NotifyDispatcher` 用 `split(",")` 解析本该是 JSON 数组的 `notify_channels`，**且从未被任何调用方触达**；`AlertNotifyServiceImpl` 把 `notified_at` set 完从不 save、收件人硬编码 `admin@dataviz.com`；三个 notifier 只 `log.info` 不发网络包。现在：`AlertNotifier` 接口 + 四实现，逐渠道查**启用中**的 `notify_channel` 行，每渠道独立 try/catch，结果（含真实 recipient 与失败原因）写 `alert_notify_log`。

两处刻意"失败得诚实"：
- **钉钉**：失败也返回 **HTTP 200**，所以必须解析 body 的 `errcode` —— 只看状态码会把"关键字不合规/被踢出群"记成发送成功。留痕时 `access_token` 打码。
- **Email / SMS**：离线 Maven 仓库里**没有** `jakarta.mail` / `spring-boot-starter-mail` ⇒ 与其写个假发送，不如直接抛 `SERVICE_UNAVAILABLE` 并记 FAILED（见 API-20）。
- 通知文本**不含 `metric_expression`**：SQL 不该出现在群聊和邮件里。

编译证据：`mvn -o -q -pl common/common-security,datasource-service,alert-service,gateway-service -am compile` 退出码 0。**运行时证据为零** —— 8083/8090 仍是 09-21 13:41 的旧包（D33）。

### 16.2 D45：跨服务查询客户端为什么落在 `common-core`

第三个需要"打数据源服务"的服务到位了（alert 已有一个），再复制一份就是第三次搬运 D41 的语义。落点选择：

- **放 `common-core` 而不是新建 Maven 模块**——`common-core` 已经引了 `spring-boot-starter-web`，因此**零 pom 改动、零 IDEA reimport**（新建模块要动 17 份 pom 并让用户重载工程，代价与收益不成比例）。
- **客户端自建 `RestTemplate`**（用 `RestTemplateBuilder` 现造），**不注入共享 bean**：各服务 `restTemplate` 的超时口径不一致，依赖它就是给自己埋隐式契约。alert 的 `RestClientConfig` 因此只保留 `notifyRestTemplate`（3s/10s）。
- **`@Value` 必须带默认值**（`${datasource-service.base-url:http://localhost:8083}`、`${internal.api.token:}`）：这个 `@Component` 会被**所有**扫 `com.dataviz.common` 的服务实例化，缺省即启动失败。
- **错误体解析回原始 code 再抛**：403 → 点名"内部口令不被数据源服务接受"；其余先看 body 的 `R.code`（"表不存在"必须还是"表不存在"）；transport/5xx 才判 503。
- **代价如实登记**：alert 侧错误前缀由 `指标取数失败` 变成 `数据源查询失败`（语义更准，但对用户是可见文案变化）。
- **Spring 陷阱**：不归档 alert 那份就会有两个同类型 `@Component` ⇒ 按类型注入即歧义、启动炸。已按 D40 连同 `.class` 移入 `backend/_archive/alert-datasource-client-20260922/{src,target-classes}/`。

### 16.3 OLAP 从"假绿"到真执行，并把注入面一起收口

旧实现（API-4）：`SqlBuilder.resolveTableName()` 返回 `"dataset_" + id`（**库里根本没这张表**），`QueryEngine.executeQuery()` 里 `rows = new ArrayList<>(); rowCount = 0`，注释写着 "In production, execute SQL via datasource-service" ⇒ `/api/analysis/query/execute` **恒 0 行**、导出只有表头。它不是"报错"，是**看起来正常地返回空**，这正是最难发现的一类壳。

新链路 `元数据 → 建 SQL → 权限改写 → 查缓存 → 内部接口执行 → 回填`：

1. `ModelServiceClient` 取 `DatasetMeta`：`null` → **404**；`datasourceId` 为空 → **400**（不猜库）；跨租户 → **403 `无权访问该数据集`**（`tenantId` 为空的内部报表路径跳过该守卫，源码注释已说明）。
2. `SqlBuilder.buildSql(dto, meta)`。**关键判据**：SQL 是**字符串经 HTTP 送出、没有任何参数绑定**，所以注入面不能靠"调用方是内部服务"来兜，五个片段全部白名单、**不匹配就抛 400 而不是拼接**：

| 片段 | 收口方式 |
|------|---------|
| 操作符 | 固定映射表，符号与英文词双写：`=,eq,!=,ne,<>,>,gt,>=,gte,<,lt,<=,lte,like,notlike,in,notin,between,notbetween,isnull,isnotnull`；表里没有 → 400。`in/notin` 走 `asList()` 逐项校验，`between` 要求两元素 |
| 聚合函数 | 只允许 `sum/avg/count/max/min` 与 `count_distinct`（→ `COUNT(DISTINCT x)`）；HAVING 侧再限 `COMPARISON_ONLY` |
| 排序方向 | 只允许 `ASC`/`DESC`（大小写归一后查表） |
| 标识符 | `column()` 先剥掉非 `[A-Za-z0-9_]` 字符，剥空即 400；表名必须整串匹配 `[A-Za-z_][A-Za-z0-9_]{0,63}`，否则 400 |
| 字面量 | `escapeString()`：拒 >1024 字符、拒控制字符，**先双写反斜杠再双写单引号**；LIKE 另转义 `%`/`_`；数值走 `numericLiteral()`（不接受任意字符串） |

   `FROM` 只允许"合法表名"或"单条 SELECT"（自定义 SQL 包成 `( … ) t_source`，多语句/非 SELECT 直接 400）；结果**一律带 `LIMIT`**（默认 1000、上限 5000）。
3. 缓存**终于被接上**（旧代码读了就扔）：key = `query:cache:{tenant}:{user}:{sha256(最终 SQL)}`——用最终 SQL 是为了让权限改写也进 key；`analysis.query-cache.ttl-seconds` 默认 60s，`≤0` 关闭；**读写缓存失败只 `log.warn` 并继续查库**（一个缓存不得把一次好查询变成 500）。
4. 执行结果**如实回填** `columns/rows/rowCount/sql/executionTime`（旧的 `sql` 字段回的是假表名 SQL，等于把 bug 印在响应里）。
5. **导出是顺手一起修好的**（本行原文曾把 export 列为"同类空壳未覆盖"，实测不成立）：`ExportController` 的 Excel(42 行)与 CSV(107 行)调的就是同一个 `queryEngine.execute()` ⇒ OLAP 通了它自然有数据。但**行数上限同一口径**：导出也吃 `ROWS_CEILING=5000` 与 API-23 的静默截断 ⇒ **"导出全量"目前不成立**，这一点在 16.6 B5 之后应作为独立事项告知用户。

### 16.4 ★ "串库为什么看不出来"——本轮最值得记的一条排障结论

`DatasetServiceImpl.previewDataset` 原来注入本服务的 `JdbcTemplate` 直查 ⇒ **连接固定落在 `db_model`**，`dataset.datasource_id` 从头到尾没参与；`QueryServiceImpl.java:56-63` 同样**收了 `datasourceId` 却完全不用**（该字段还挂着 `@NotNull(message = "数据源ID不能为空")`，报错文案甚至写着"数据源 ID 必填"，代码却不读它 ⇒ 立 **API-22**）。

为什么这个错从来没被发现：**结果两边一模一样**。

| 对象 | `db_model`（基表） | `db_analysis`（Y1 建的透传视图） |
|------|-------------------|--------------------------------|
| `demo_sales_daily` | 135 行，`SUM(amount)=3956715.00` | 135 行，`SUM(amount)=3956715.00` |
| `demo_orders` | 125 行，`SUM(pay_amount)=268793.75` | 125 行，`SUM(pay_amount)=268793.75` |

⇒ **"数一数对不上"这类验收在这一刻失效**。更诚实的一句：`db_analysis` 那三张是**我自己在 Y1 建的视图**，`VIEW_DEFINITION` 就是 `SELECT * FROM db_model.demo_x`，基表其实只在 `db_model` 一处 ⇒ 所以"结果相同"**既不是巧合也绝不能被当成"路由正确"的证据**，它只说明这条验收路径没有区分度。

因此 16.6 的路由判据换成**结构差异**而不是数值差异：`model_dataset` 这张表**只在 `db_model` 里存在**，所以同一条 SQL 打 ds 902（→ `db_model`）应成功、打 ds 901（→ `db_analysis`）必须以"表不存在"失败。这一条不需要登录态、不需要改数据，且失败本身就是证据。

（附带修正一条旧口径：`information_schema.tables.TABLE_ROWS` 对这三张视图直接给 `NULL` —— D35 说它是估算值，这里更进一步：对视图根本没有估算值。）
