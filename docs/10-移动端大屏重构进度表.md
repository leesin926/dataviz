| **screen 实时推送** | `screen-service/…/ScreenDataPusher.java:11-16` `@Scheduled(fixedDelay=5000)` 方法体两行 TODO | "大屏实时刷新"只能靠前端轮询，WebSocket 推送不成立 |
| **collab 审批** | `ApprovalController` **无 service 层**，只用 mapper 直接改 `status` | 无流转、无通知、无校验；且前端零入口 |
| **admin License** | `LicenseController.java:33 activate()` 恒 success、`validateLicense()` 恒 `valid:true` | 授权校验形同不存在（演示可过，生产即漏洞） |

⇒ **结论**：这些和第一章"记录不修"的 API-4 / API-6 / API-16 是同一批事实 —— 它们不是漏修，而是**跨服务新功能**，需要单独立项排期。

> ⚠️ **对本节上一版结论的更正（阶段 AA 期间发现，我先前说错过一次）**：我曾把 analysis / etl / alert 归因为"缺一块共用的**执行 SQL 底座**"。这是**错的** —— datasource-service 早就有真执行器（`DatasourceServiceImpl.executeQuery`：Hikari 池、SELECT/SHOW/DESCRIBE 只读白名单、`setQueryTimeout` + `setMaxRows`，返回 `{columns,rows,rowCount,executionTime,sql}`），**缺的只是"调用方"**。AA 因此没有重造底座，只加了一个内部端点（AA2）+ alert 侧的客户端（AA3）。剩下的 etl / analysis 同样可以复用这条链路，工作量比"造底座"小一个量级。
