### 1.1 出包过程中的一次自伤（已登记，别重复踩）

为了补 zip，先用 `--prepackaged release/win-unpacked` 打包，得到 8.6 MB 的"zip"。那是**假成功**：`unzip -l` 只有 8 个条目、没有主程序 exe。根因是先前两次构建在 `EnsureEmptyDir` 阶段清空了 `release/win-unpacked`，唯一没被删掉的就是被进程占用的 `app.asar`。所以：

1. 那份 8.6 MB 的 zip 已改名为 `DataViz Desktop-1.0.0-x64.zip.incomplete-20261018` 留在 `release/`，**不要分发**。
2. `release/win-unpacked/` 现在只剩 7 个文件，且目录被一个第三方句柄（`crashpad_handler_.exe`，父进程 `TsService.exe`，创建于 2026-10-16）占用，`mv`/`rm` 都返回 *Device or resource busy*。**重启机器后才能清理**。在此之前，任何往 `release/` 全量重打包的构建都会失败在同一个位置 —— 出包请改用一个新目录（`-c.directories.output=<新目录>`），或先确认没有实例在跑。
3. 正确做法是**直接重新 packaging**（`npx electron-builder --win zip -c.directories.output=release-green-pack`），产物 104.7 MB 且 `unzip -t` 通过，再移入 `release/`。`--prepackaged` 只在"确信 unpacked 目录完整"时用。

## 二、两种分发形态的分工

| | 安装版（NSIS） | 绿色版（zip） |
|---|---|---|
| 适合谁 | 长期使用的业务用户、需要开始菜单/桌面图标（`shortcutName: DataViz 桌面端`） | 试用、大屏机器、演示机、被 IT 限制装软件的环境 |
| 安装方式 | `oneClick: false` + `allowToChangeInstallationDirectory: true` ⇒ 有向导、可选目录，装到当前用户（`perMachine: false`，不需要管理员） | 解压即用 `DataViz Desktop.exe` |
| 卸载 | 控制面板/开始菜单卸载项 | 删目录即走 |
| 用户数据 | 两者共用 `%APPDATA%/dataviz-desktop`（`deleteAppDataOnUninstall: false` ⇒ 卸载**不**删离线大屏缓存、导出目录记录、`dataviz_api_base`、`updates.json`） | 同 |
| 覆盖升级 | 需先关旧实例；NSIS 会替换安装目录 | 解压到新目录，旧目录留着当回退 |

要点：**同一份 userData 被两个形态共用**。给大屏机器发绿色包、给办公机发安装版，是安全的（同版本时）；不同版本混用会让 A 端写的缓存被 B 端读到，`cache.js` 没有版本维度 ⇒ 混版期请让用户清缓存（应用内"设置-清缓存"，走 `cache:clear`）。

## 三、未签名的代价（`win.signAndEditExecutable: false` 是明确选择，不是遗漏）

这个开关关掉的是"用 winCodeSign 给 exe 签名并写入版本资源/图标"。代价按可感知程度排：

1. **SmartScreen 蓝条 + 杀软启发式**：首次下载运行会出"Windows 已保护你的电脑"，需要"仍要运行"；部分企业 EDR 会把未签名的 `DataViz Desktop.exe` 报为可疑。**这也是本轮目录被外部句柄锁住的直接嫌疑**。
2. **没有版本资源**：右键 `DataViz Desktop.exe` → 属性里文件版本/产品名称是 Electron 默认值。所以**判断装的是哪一版不能看 exe 属性**（见 §五）。
3. **没有自定义图标**：任务栏/桌面快捷方式用 Electron 默认图标。`buildResources: "build"` 目录当前不存在，补图标只需放 `build/icon.ico`（≥256×256）再重新出包。
4. **安装版无法做发布者校验**：用户只能靠哈希核对（§六）。

要摘掉这些代价的顺序（都不在本轮范围，登记为待决策）：代码签名证书（OV，或内网自建 CA + 组策略信任根证书）→ 打开 `signAndEditExecutable` → 配 `publish` → 引入 `electron-updater` 做真下载安装。**在没有证书之前，不要打开这个开关**：electron-builder 会在签名步骤失败或者静默跳过，症状是"构建成功但产物没变"。

## 四、更新通道设计

### 4.1 现状（代码事实）

`electron/updater.js` 是**只检查、不安装**的实现，且这是文件头写死的两条硬约束：没有可用更新源、没有签名与下载链路。行为：

- 更新源来自**每台机器本地**的 `%APPDATA%/dataviz-desktop/updates.json`（`{"feedUrl":"http://..."}`），由界面写（IPC `updater:setFeed`），不是烤进包里的。
- `updater:check` 拉 `${feedUrl}/latest.yml`，只解析 `version` / `path` / `sha512` 三行，与当前版本比（`compareVersions` 逐段整数比较）。
- 三种结果如实回报：`not-configured`（没写 feedUrl，带提示路径）、`available`/`up-to-date`（`available` 一定带 `note: 本版本只检查不安装…`）、失败带原因（连不上、非 200、超时 8 s、缺 version）。
- `package.json#build.publish` 里那条 `url: http://REPLACE-WITH-INTRANET-HOST/updates/win32` **只是让 electron-builder 生成 latest.yml 用的占位符**，运行时没人读它。别把它当成"更新通道已配置"。

### 4.2 推荐路线（甲：内网静态目录 + 现有 check）

准备一个内网 HTTP 目录（Nginx/IIS/文件服务器均可，只要能列目录且不做鉴权重定向——`fetchText` 只跟随 3xx 的 `Location`，但鉴权 401 会被如实报成"更新源返回 401"）：

```
http://dataviz-update.<内网域>/updates/win32/
├── latest.yml
├── DataViz Desktop-Setup-1.0.1.exe
└── DataViz Desktop-Setup-1.0.1.exe.blockmap   ← 留着头脑清楚，将来上 electron-updater 差分才用得上
```

发版动作（每次）：

1. 改 `apps/pc-desktop/package.json` 的 `version`（`1.0.0` → `1.0.1`），**必须**同步改，否则 `latest.yml` 的 version 不变、客户端永远 `up-to-date`。
2. 重新构建渲染层（`npm run build` = `vue-tsc --noEmit && vite build`）后 `npx electron-builder --win nsis`；目录被占时换 `-c.directories.output`。
3. **现场核对** `latest.yml` 的 `sha512` 与新 exe 的实测哈希一致（本轮已核对过一次，是有效门禁）。
4. 把 `latest.yml` + exe（+ blockmap）一起上传到同一目录。**只传 exe 不传 latest.yml = 用户查不到；只传 latest.yml = 用户查到但下载不到**（当前不下载，但这条留给下一步）。
5. 客户端侧无需动作：下一次 `updater:check` 就能看到新版本号。

**为什么不选乙/丙**：乙（共享盘/文件服务器鉴权面）会把更新源变成需要凭据的东西，`updates.json` 里存明文凭据是新的泄露面；丙（完全不做更新，只在界面显示"请重新下载"）在演示机分散的场景运营成本更高。甲的成本只是一个静态目录。

**下一步（未做）**：把 `check` 之后接到"下载 exe → 校验 sha512 → 启动安装器"。下载与校验可以自研（`https.get` 到临时目录 + `crypto` 哈希），但**装之前必须校验哈希**，而且这条路在签名前会一路撞 SmartScreen，所以真做之前先定签名。

## 五、服务地址注入（桌面端特有的一条）

打包后窗口 origin 是 `file://`，相对 `/api` 解析成 `file:///api`，请求根本出不了本机（`src/desktop/apiBase.ts` 的注释就是为这件事写的）。解析优先级：

```
构建期 VITE_API_BASE_URL  >  本机 localStorage 的 dataviz_api_base  >  相对 /api
```

本轮实测：**仓库里没有 `.env` / `.env.production`** ⇒ `VITE_API_BASE_URL` 未被烤入，当前这两个产物装到任何机器上，首启动都落在 `/api`，`baseLooksUnusable()` 为真（`file:` 且非 `http(s)`），界面直接显示"接口地址不可用"并要求在首页填一次（`src/views/Home.vue:97` 调 `applyBase`）。这是**设计内**的降级，不是坏：地址错了改一次即可，不必重新出包。

三种注入方式怎么选：

| 方式 | 做法 | 代价 |
|------|------|------|
| 运行时手输（现状） | 首页填 `http://<网关>:8080/api` | 每台机器一次人工输入；内网地址是常识信息，不敏感 |
| 烤默认值 | 出包前建 `apps/pc-desktop/.env.production` 写 `VITE_API_BASE_URL=http://<网关>:8080/api` | 换网关就要重出包；**运行时覆盖仍生效**，所以只是省掉首次输入 |
| 预置配置 | 部署脚本往 `%APPDATA%\dataviz-desktop\` 放配置文件 | 目前 apiBase 读的是 localStorage，改读文件需要动代码 |

建议：**内网有稳定网关地址就烤默认值**（第二行），因为它不改变可覆盖性，只是把"首次必须手输"这条隐性验收项消掉。校验规则不变：`validateBase` 只接受 `http(s)://` 绝对地址或以 `/` 开头的相对路径，其它（含 `javascript:`）直接抛错，不会写进 axios。

⬜ 本轮没有跑"装完后填地址→列表出真数据"的端到端判据（需要登录与真实网关地址），属用户侧验收（§七 D2）。

## 六、验收判据（分发前必须有的三条）

**D1 完整性核对（免登录，任何人都能跑）** —— 拿到包先比哈希，再比体积：

```bash
node -e "const c=require('crypto'),f=require('fs');const b=f.readFileSync(process.argv[1]);
console.log(b.length, c.createHash('sha512').update(b).digest('base64'))" "DataViz Desktop-Setup-1.0.0.exe"
# 期望：76887542 + latest.yml 里那串 sha512
```

绿色版没有 latest.yml 兜着，所以上表 §一 的 zip sha512/sha256 就是它的核对值——**分发绿色包时必须同时把这两个值贴在下载说明里**，未签名场景下这是唯一的来源证明。

**D2 装完能连上（登录侧）**：装/解压 → 打开 → 首页显示"接口地址不可用"（未烤默认值时）→ 填网关地址 → 大屏列表出真数据 → 导出一次 PNG/PDF 落盘。这一串是 AW4/AX 系列一直在等用户跑的登录态判据，本文件不代替。

**D3 更新提示对不对（免登录，但要一台有网可达更新源的机器）**：`updates.json` 写 `feedUrl` 后点"检查更新"，四种读数必须各归各位：没写 → `not-configured` 并显示配置文件路径；版本相同 → `up-to-date`；`latest.yml` 版本更高 → `available` **且界面上能看到那句"本版本只检查不安装"**（这句话被吞掉就是假成功）；地址填错/服务挂了 → 失败原因里带 `更新源返回 xxx` 或超时文案。

## 七、回退与版本判据

**怎么确认某台机器装的是哪一版**（未签名 exe 没有版本资源，所以不能看属性）：

1. 应用内"关于/设置"读 `app:info`（`electron/main.js:304`）返回的 `version` —— 这是 app.version，等于 package.json 的 `version`。
2. 安装目录里 `resources/app.asar` 的字节数（本轮 2 910 874）+ 该文件修改时间，可以粗判是不是同一次构建的产物。
3. 绿色版看解压目录里 zip 的来源哈希（§一）。

**回退**：

- 安装版：控制面板卸载（userData 不会被删，`deleteAppDataOnUninstall: false`），再装旧 exe。旧 exe 要从更新目录里保留一份**上一版**（约定：更新目录只留最近两版，更早的移到归档目录，不删）。
- 绿色版：解压目录带版本号，切回旧目录即可；**不要覆盖解压**（同目录混放两版会把旧 `resources/app.asar` 换新，回退就没了）。
- 服务端没有版本耦合（桌面端只是前端 + 本地缓存），所以客户端回退不需要后端配套动作；**唯一例外**是这一轮之后新增的 IPC/接口字段（如导出、审批中心），旧包读新接口可能 404，症状是"页面空白"而不是报错，回退前先看 `latest.yml` 的时间是否跨越了后端变更。

**版本推进约定（建议）**：`1.0.z` 修问题、`1.1.0` 加界面能力。每次发版在三本台账（`docs/10`、`docs/12`、`devlog/EDIT_LOG.md`）记：版本号、exe 与 zip 的字节数 + sha512、更新目录路径、这一版对应哪个后端提交区间。
